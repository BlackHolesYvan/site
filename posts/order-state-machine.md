# 订单状态机设计：从十余个退款状态谈到事务一致性

> 本文以招生 CRM 与订单交易中台的真实改造为素材，记录一次三层状态机的设计取舍。

## 为什么需要三层状态机

订单、退款单、审批流是三个**生命周期不同**的对象：

- **订单**关注履约：待支付、已支付、履约中、已完成、已关闭。
- **退款单**关注资金回流：仅退款单就有十余个状态，横跨发起、审核、放款、到账。
- **审批流**关注"人"的决策：申请 → 团队长 → 总经办 → 财务放款，支持逐级激活、驳回恢复。

把三者混在一张订单表的 `status` 字段里，是早期单体最容易犯的错误：字段会迅速膨胀成"状态笛卡尔积"，没人说得清某个值到底意味着什么。

## 三条工程纪律

### 1. 状态流转必须在数据库事务内完成

```go
err := db.Transaction(func(tx *gorm.DB) error {
    // 前置校验：只有"待审核"才允许进入"审核中"
    if err := checkRefundStatus(tx, id, StatusPending); err != nil {
        return err // 回滚，杜绝并发脏写
    }
    if err := updateRefundStatus(tx, id, StatusApproving); err != nil {
        return err
    }
    return writeAuditLog(tx, id, "refund.approve.start")
})
```

状态前置校验 + 事务，二者缺一不可。只做校验不加事务，并发下会出现两个请求同时通过校验的"双写"窗口。

### 2. 金额统一以"分"存储

浮点误差在退款返利场景是事故级问题。所有金额字段用整型存分，仅在展示层格式化为元。

### 3. 每一步都要留痕

审批的每一次激活、驳回、重新发起都写审计日志。半年后财务来对账，你能回答"谁在什么时候把哪一笔退款推到了哪一步"。

## 小结

状态机不是设计模式考试题，而是**复杂业务的防错底线**：边界划清、事务兜住、金额用分、操作留痕。做到这四点，订单系统才能撑得起"迁移期双轨并行"这种高难度动作。
